## Принятые ограничения

- Существующие публичные URL, SEO-метаданные и содержимое опубликованных страниц сохраняются.
- `Pages.path` остаётся источником публичного URL. Родительская связь используется для редакционной структуры и не переписывает адреса автоматически.
- Типы блоков и их визуальная система остаются типизированными в коде; тексты и параметры каждого размещения редактируются в Payload.
- Миграции контента сначала запускаются в режиме отчёта. Неоднозначные записи не меняются автоматически.
- Сначала внедряется Live Preview всей страницы. Точное отображение блоков непосредственно в текстовом полотне вынесено в отдельный этап после проверки базового preview.
- До любых изменений Next.js агент читает соответствующее руководство из `node_modules/next/dist/docs/` согласно `AGENTS.md`.

## Порядок работ

### Этап 0. Предварительная инвентаризация и безопасный запуск

1. Проверить текущие конфигурации `Pages`, Lexical, блоков, публичного рендера, draft mode, импорт-карты Payload и доступов.
2. Снять резервную копию БД перед миграцией содержимого.
3. Сформировать отчёт по страницам: опубликованные и черновики, `CMS_BLOCK_n`, типы legacy-блоков, наличие `legacyMarkdown`, страницы без родителя по URL-структуре, заполненность SEO-полей.
4. Зафиксировать контрольный набор статей разных типов: с таблицей, FAQ, предупреждением, баннером, внутренними ссылками и без legacy-блоков.
5. Согласовать базовый вариант таблиц: начать с `EXPERIMENTAL_TableFeature`, уже экспортируемого установленной версией Lexical; если пилот выявит потерю данных или нестабильное редактирование, использовать единый типизированный блок таблицы для статей.

**Готово, когда:** есть резервная копия, отчёт инвентаризации и список страниц для ручной проверки. На этом этапе данные не изменяются.

### Этап 1. Заменить миграционные заглушки настоящими блоками

Файлы для изучения: `src/lib/cms/legacy-blocks.ts`, `src/lib/cms/queries.ts`, `src/payload/collections.ts`, `src/payload/blocks.ts`.

1. Подготовить идемпотентный backfill для записей `Pages`. Это преобразование документов, а не изменение публичного URL или обычной SQL-схемы.
2. Для каждой записи с `CMS_BLOCK_n` разобрать соответствующий `legacyMarkdown` и построить настоящий Lexical block node с исходными полями и содержимым.
3. Сохранить порядок блоков относительно заголовков и абзацев. Не трогать уже настоящие блоки и записи, в которых соответствующий исходный блок определить нельзя.
4. Сначала выполнить `--dry-run`: вывести страницу, число распознанных блоков, неизвестные токены и ошибки разбора. Не выводить в лог секреты или полные тексты статей.
5. Сверить production dry-run, сохранить свежий серверный backup, выполнить backfill в live БД и повторить dry-run.
6. Сохранить `legacyMarkdown` как архив на переходный период. Оставить публичный fallback `restoreLegacyBlocks` до подтверждения, что во всех страницах с блоками сохранены настоящие узлы.

Production CLI находится в `/app/scripts/payload-tools/payload-backfill-legacy-blocks.mjs`. Для live dry-run и apply обязательны `--target-db=fms3 --allow-production`; apply дополнительно требует `--apply`. Скрипт отключает schema push, сверяет имя БД с `DATABASE_URL`, запрещает production при `NODE_ENV` отличном от `production` и разрешает записи только в точную базу `fms3`.

**Критерии приёмки:** в форме статьи нет видимых `CMS_BLOCK_n`; порядок, тексты и поля блоков совпадают с опубликованной страницей; повторный запуск backfill не меняет уже обработанные записи.

**Критерии приёмки:** таблица создаётся без Markdown-синтаксиса и JSON; после сохранения публичная версия сохраняет строки, колонки и заголовок; на мобильном экране таблица остаётся читаемой.

6. Заменить сырой `homeContent` JSON на обычные поля и массивы Payload либо на специальное понятное поле. Перенести текущие значения без потери и сверить главную страницу в Live Preview.
7. Проверить, что роли редактора и публикатора по-прежнему могут выполнять свои текущие действия после перестройки полей.

**Критерии приёмки:** редактору не нужно искать поле статьи среди миграционных данных; служебные коллекции не смешаны с материалами; главную можно редактировать без ручного JSON.

### Этап 6. Добавить редакторский SEO-чеклист

Файлы для изучения: `src/payload/fields.ts`, `src/payload/validation.ts`, `src/components/cms/CmsPageRenderer.tsx`, `src/payload/access.ts`.

1. Добавить предпросмотр поискового сниппета на основе `seo.title`, `seo.description`, canonical и публичного пути.
2. Добавить подсказки по длине SEO-заголовка и описания; не менять уже заданные значения автоматически.
3. Добавить предупреждения перед публикацией для пустого описания, отсутствия даты проверки, отсутствующего OG-изображения (если оно ожидается), битых внутренних ссылок и незаполненных обязательных для типа страницы полей.
4. Начать с предупреждений, не блокировать публикацию без согласованного редакционного правила.
5. Рассчитывать время чтения из Lexical-содержимого как предложение, сохранив редакторское значение и возможность поправить его вручную.
6. Сохранять текущую проверку безопасности пути и добавить только проверки, которые не мешают легальным исключениям и текущему содержимому.

**Критерии приёмки:** перед публикацией видны основные ошибки и поисковый сниппет; автоподсказки не перезаписывают SEO-копирайт.

### Этап 7. Рассмотреть точное отображение блоков внутри редактора

Этот этап выполнять после принятия Live Preview редакторами.

1. Сделать ограниченный прототип для `QuickAnswer`, `Notice`, `Warning` и `LegalSource`.
2. Использовать общий визуальный слой с публичными компонентами; не копировать стили в независимые реализации.
3. Для FAQ, карточек и баннера показать прототип после простых блоков. Интерактивную консультацию в редакторе отображать безопасной статической версией без запросов, аналитики и отправки формы.
4. Если прототип улучшает повседневное редактирование, подключать остальные блоки по очереди. Если Live Preview решает задачу, оставить блоки в компактном редакторском представлении.

**Критерии приёмки:** превью блока не теряет введённые значения, сохраняет фокус редактирования, визуально соответствует сайту и не запускает публичные действия.

### Этап 8. Отдельно улучшить формы настройки интерактивных инструментов

Это отдельный поток после редакторского ядра статей; текущие JSON-форматы остаются форматом хранения.

1. Разложить `Tools` на вкладки «Содержание», «Поля», «Логика», «Результаты», «Интеграция», «SEO».
2. Заменить редактирование условий, ответов тестов и маппингов JSON-полями с визуальными селекторами; оставить стабильные технические ключи под контролем.
3. Для `DataTables.rows[].values` сделать табличный ввод по определённым колонкам, сохранив период действия и источник.
4. Скрывать низкоуровневые параметры от редакторов, которым достаточно менять подписи и тексты.
5. Не менять runtime и DSL без отдельного обоснования; форма должна редактировать текущую модель данных.

**Критерии приёмки:** редактор может изменить текст и типовые значения инструмента без ручного редактирования JSON; сложные правила остаются валидируемыми текущими функциями.

## Общие правила для агента

- Выполнять этапы по порядку и не смешивать миграцию содержимого с изменением визуального шаблона.
- На каждом этапе сначала показать затронутые модели и способ сохранения обратной совместимости, затем менять код.
- Для миграций контента сначала делать отчёт и dry run; при неизвестном формате останавливать только соответствующие записи и сохранять их для ручного разбора.
- Не менять URL существующих страниц без отдельного согласования.
- После этапов 1–4 вручную сверять контрольные статьи в админке и в preview; после каждого этапа фиксировать результат и список оставшихся записей.
- Этапы 7 и 8 не блокируют публикацию первых улучшений редактора статей.
