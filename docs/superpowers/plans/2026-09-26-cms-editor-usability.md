# План улучшения редактора и управления контентом Payload

## Цель

Сделать ежедневную работу со статьями понятной редактору: реальные блоки вместо `CMS_BLOCK_n`, визуальное создание таблиц, просмотр черновика в оформлении сайта, иерархия страниц, меньше технических полей и понятные SEO-подсказки.

## Текущий прогресс

- Этап 0 завершён: конфигурация, MDX-источники и live Pages production-БД `fms3` проинвентаризированы read-only запросами; защищённый серверный backup успешно восстановлен в изолированный PostgreSQL 16, счётчики копии совпали с baseline.
- Production-схема и документы Pages не менялись. Дамп не передавался на рабочую машину; локального PostgreSQL и работающего Docker daemon нет. Подробный отчёт, контрольные маршруты, путь и проверочная сумма backup: [этап 0](2026-09-26-cms-editor-usability-stage-0-inventory.md).
- Перед подключением Payload к тестовой копии обязательно выставить `PAYLOAD_DB_PUSH=false`; перед этапом 1 восстановить отдельную тестовую БД из сохранённого backup. Не подключать разработческую конфигурацию к production.
- Реализация и повторный запуск этапа 1 ранее проверены на восстановленной копии: `--dry-run` нашёл 40 вариантов с 327 маркерами (313 опубликованных и 14 черновых блоков), `--apply` обновил их, а повторный dry-run не нашёл работу. По прямому решению пользователя дальнейшая работа ведётся в production без новых копий БД; backfill production будет выполнен после свежего backup и проверки production dry-run.
- Перед этим переходом в production этап 1 ещё не был применён к live Pages. Свежий production backup хранится на сервере отдельно от приложения; путь и checksum записываются в отчёт после проверки backfill.
- Для CLI добавлен ESM runner и production-бандл для Docker runtime: установленный `tsx` загружал MDX parser как CommonJS и падал на ESM-only `estree-walker`; скрипт собирает TypeScript-модули через `esbuild`, а `next/cache` подменяется безопасным no-op только для CLI. Schema push отключается; production требует точные `--target-db=fms3`, `--allow-production` и `NODE_ENV=production`.
- SSH-ключ остаётся разрешённым на весь план по просьбе пользователя; production-доступы не менялись.

## Принятые ограничения

- Существующие публичные URL, SEO-метаданные и содержимое опубликованных страниц сохраняются.
- `Pages.path` остаётся источником публичного URL. Родительская связь используется для редакционной структуры и не переписывает адреса автоматически.
- Типы блоков и их визуальная система остаются типизированными в коде; тексты и параметры каждого размещения редактируются в Payload.
- Миграции контента сначала запускаются в режиме отчёта. Неоднозначные записи не меняются автоматически.
- Сначала внедряется Live Preview всей страницы. Точное отображение блоков непосредственно в текстовом полотне вынесено в отдельный этап после проверки базового preview.
- До любых изменений Next.js агент читает соответствующее руководство из `node_modules/next/dist/docs/` согласно `AGENTS.md`.

## Порядок работ

### Этап 0. Предварительная инвентаризация и безопасный запуск

1. Проверить текущие конфигурации `Pages`, Lexical, блоков, публичного рендера, draft mode, импорт-карты Payload и доступов.
2. Снять резервную копию БД перед миграцией содержимого.
3. Сформировать отчёт по страницам: опубликованные и черновики, `CMS_BLOCK_n`, типы legacy-блоков, наличие `legacyMarkdown`, страницы без родителя по URL-структуре, заполненность SEO-полей.
4. Зафиксировать контрольный набор статей разных типов: с таблицей, FAQ, предупреждением, баннером, внутренними ссылками и без legacy-блоков.
5. Согласовать базовый вариант таблиц: начать с `EXPERIMENTAL_TableFeature`, уже экспортируемого установленной версией Lexical; если пилот выявит потерю данных или нестабильное редактирование, использовать единый типизированный блок таблицы для статей.

**Готово, когда:** есть резервная копия, отчёт инвентаризации и список страниц для ручной проверки. На этом этапе данные не изменяются.

### Этап 1. Заменить миграционные заглушки настоящими блоками

Файлы для изучения: `src/lib/cms/legacy-blocks.ts`, `src/lib/cms/queries.ts`, `src/payload/collections.ts`, `src/payload/blocks.ts`.

1. Подготовить идемпотентный backfill для записей `Pages`. Это преобразование документов, а не изменение публичного URL или обычной SQL-схемы.
2. Для каждой записи с `CMS_BLOCK_n` разобрать соответствующий `legacyMarkdown` и построить настоящий Lexical block node с исходными полями и содержимым.
3. Сохранить порядок блоков относительно заголовков и абзацев. Не трогать уже настоящие блоки и записи, в которых соответствующий исходный блок определить нельзя.
4. Сначала выполнить `--dry-run`: вывести страницу, число распознанных блоков, неизвестные токены и ошибки разбора. Не выводить в лог секреты или полные тексты статей.
5. После сверки production dry-run и свежего серверного backup выполнить backfill в live БД (по прямому решению пользователя), затем открыть статьи в админке и убедиться, что поля блоков редактируются отдельно.
6. Сохранить `legacyMarkdown` как архив на переходный период. Оставить публичный fallback `restoreLegacyBlocks` до подтверждения, что во всех страницах с блоками сохранены настоящие узлы.

CLI локально для разрешённой loopback restore-копии: `npm run payload:backfill:legacy-blocks -- --dry-run`; production-бандл запускается внутри production-контейнера. Для live dry-run и apply обязательны `--target-db=fms3 --allow-production`; apply дополнительно требует `--apply`. Скрипт отключает schema push, сверяет имя БД с `DATABASE_URL`, запрещает production при `NODE_ENV` отличном от `production` и разрешает записи только в точную базу `fms3`.

**Критерии приёмки:** в форме статьи нет видимых `CMS_BLOCK_n`; порядок, тексты и поля блоков совпадают с опубликованной страницей; повторный запуск backfill не меняет уже обработанные записи.

### Этап 2. Добавить редактор таблиц для статей

Файлы для изучения: `src/payload.config.mts`, `src/components/cms/LexicalRenderer.tsx`, `src/app/(site)/globals.css`, `src/payload/collections.ts`.

1. Включить Lexical Table Feature только для поля статьи `Pages.content`; сохранить остальные разрешённые функции и блоки.
2. Обновить import map штатным скриптом проекта после регистрации клиентской части функции.
3. Проверить создание таблицы через меню редактора, добавление/удаление строк и колонок, редактирование ячеек, сохранение и повторное открытие документа.
4. Сверить узлы таблицы в сохранённом содержимом с тем, что понимает публичный `LexicalRenderer`.
5. Доработать рендер таблицы: корректные ячейки заголовка, горизонтальная прокрутка на узком экране и существующие стили `.mdx-prose`.
6. Если экспериментальная функция не проходит ручной пилот, заменить её на отдельный блок «Таблица в статье» с вводом заголовков и строк в сеточном интерфейсе. Не использовать для этого `DataTables`: эта коллекция обслуживает расчёты инструментов.
7. Переименовать подписи технической коллекции в админке, например «Таблицы инструментов», чтобы редактор не принимал её за таблицы статей.

**Критерии приёмки:** таблица создаётся без Markdown-синтаксиса и JSON; после сохранения публичная версия сохраняет строки, колонки и заголовок; на мобильном экране таблица остаётся читаемой.

### Этап 3. Настроить Live Preview черновиков

Файлы для изучения: `src/payload.config.mts`, `src/lib/cms/queries.ts`, `src/app/(site)/[...slug]/page.tsx`, `src/app/(site)/page.tsx`, `src/components/cms/CmsPageRenderer.tsx`, `src/components/cms/CmsToolPage.tsx`.

1. Настроить Payload `admin.livePreview` для `Pages`, с динамическим URL из `path` и desktop/mobile breakpoints.
2. Подключить live-preview интеграцию, чтобы изменения формы поступали в iframe и проходили через тот же `CmsPageRenderer`, что и опубликованная страница.
3. Добавить безопасный вход в Next Draft Mode и выход из него. Проверить, что черновик доступен только через подписанный/проверенный Payload preview flow; обычный посетитель продолжает получать только опубликованный документ.
4. Использовать существующие `getPageByPath(path, draft)` и `draftMode()` там, где это подходит; не читать черновики по открытому публичному query-параметру.
5. В preview отключить отправку заявок, внешние вызовы чата и аналитические события, сохранив статический вид баннеров и страницы.
6. Предусмотреть понятное состояние для ещё не опубликованного URL, ошибки загрузки и закрытого preview.

**Критерии приёмки:** редактор открывает черновик из CMS, видит реальный шаблон сайта, изменения заголовка, текста и блоков появляются до публикации; мобильный режим доступен; публичный анонимный запрос не раскрывает черновик.

### Этап 4. Добавить иерархию страниц и связи между материалами

Файлы для изучения: `src/payload/collections.ts`, `src/payload/blocks.ts`, `src/components/cms/LexicalRenderer.tsx`, `src/lib/cms/queries.ts`, `src/components/cms/CmsPageRenderer.tsx`.

1. Проверить совместимость `@payloadcms/plugin-nested-docs` с установленным Payload 3.88.0 и решить, использовать ли плагин или простую собственную parent-связь.
2. Добавить необязательную связь «Родительская страница» и порядок среди соседних страниц. Не выводить `path` из родителя автоматически.
3. Сопоставить текущие страницы с родителями по существующим URL-сегментам только там, где есть однозначная опубликованная страница-родитель. Остальные оставить без родителя и вывести в отчёт для ручного назначения.
4. Добавить редакционный вид дерева: вложенные названия, статус и путь, быстрый переход к редактированию, поиск. Один только список с колонкой «Родитель» не считать достаточной заменой дерева.
5. Сформировать хлебные крошки из редакционной иерархии, отдельно проверить соответствие URL и существующей навигации сайта.
6. Задействовать существующее `relatedPages` в публичном выводе либо удалить его из редакторской формы. Предпочтительный вариант — использовать его для подборки связанных материалов.
7. В `relatedGuide` и `linkCardGrid` заменить ручной ввод внутреннего URL выбором страницы; при необходимости оставить редактируемые подпись и описание. Существующие текстовые ссылки мигрировать с сохранением отображаемого текста и URL.

**Критерии приёмки:** редактор видит иерархию в дереве и в форме; публичные адреса не изменились; блоки перехода ведут на выбранные страницы; неизвестные или битые внутренние ссылки отображаются в отчёте.

### Этап 5. Упростить форму редактирования и навигацию Payload

Файлы для изучения: `src/payload/collections.ts`, `src/payload/globals.ts`, `src/payload/fields.ts`, `src/payload.config.mts`.

1. Разделить форму страницы на вкладки: «Основное», «Контент», «SEO», «Связи», «Импорт». Сгруппировать URL, тип и служебные метаданные так, чтобы главное поле «Контент» было легко найти.
2. Для `kind` показать только применимые поля и явно пояснить отличие статьи, лендинга, правовой страницы и политики.
3. Проверить `CmsPageRenderer`: определить ожидаемое поведение для `kind: legal`, так как сейчас отдельную ветку получают только landing и policy; согласовать шаблон до изменения публичного вывода.
4. Скрыть readonly `legacyMarkdown` и импортные `sourceKey` от обычного редакторского потока, сохранив доступ администраторам в отдельной вкладке.
5. Разложить навигацию CMS по группам: «Материалы», «Инструменты», «Служебное». Назначить `Users` и `RuleTestCases` только соответствующим ролям.
6. Заменить сырой `homeContent` JSON на обычные поля и массивы Payload либо на специальное понятное поле. Перенести текущие значения без потери и сверить главную страницу в Live Preview.
7. Проверить, что роли редактора и публикатора по-прежнему могут выполнять свои текущие действия после перестройки полей.

**Критерии приёмки:** редактору не нужно искать поле статьи среди миграционных данных; служебные коллекции не смешаны с материалами; главную можно редактировать без ручного JSON.

### Этап 6. Добавить редакторский SEO-чеклист

Файлы для изучения: `src/payload/fields.ts`, `src/payload/validation.ts`, `src/components/cms/CmsPageRenderer.tsx`, `src/payload/access.ts`.

1. Добавить предпросмотр поискового сниппета на основе `seo.title`, `seo.description`, canonical и публичного пути.
2. Добавить подсказки по длине SEO-заголовка и описания; не менять уже заданные значения автоматически.
3. Добавить предупреждения перед публикацией для пустого описания, отсутствия даты проверки, отсутствующего OG-изображения (если оно ожидается), битых внутренних ссылок и незаполненных обязательных для типа страницы полей.
4. Начать с предупреждений, не блокировать публикацию без согласованного редакционного правила.
5. Рассчитывать время чтения из Lexical-содержимого как предложение, сохранив редакторское значение и возможность поправить его вручную.
6. Сохранять текущую проверку безопасности пути и добавить только проверки, которые не мешают легальным исключениям и текущему содержимому.

**Критерии приёмки:** перед публикацией видны основные ошибки и поисковый сниппет; автоподсказки не перезаписывают SEO-копирайт.

### Этап 7. Рассмотреть точное отображение блоков внутри редактора

Этот этап выполнять после принятия Live Preview редакторами.

1. Сделать ограниченный прототип для `QuickAnswer`, `Notice`, `Warning` и `LegalSource`.
2. Использовать общий визуальный слой с публичными компонентами; не копировать стили в независимые реализации.
3. Для FAQ, карточек и баннера показать прототип после простых блоков. Интерактивную консультацию в редакторе отображать безопасной статической версией без запросов, аналитики и отправки формы.
4. Если прототип улучшает повседневное редактирование, подключать остальные блоки по очереди. Если Live Preview решает задачу, оставить блоки в компактном редакторском представлении.

**Критерии приёмки:** превью блока не теряет введённые значения, сохраняет фокус редактирования, визуально соответствует сайту и не запускает публичные действия.

### Этап 8. Отдельно улучшить формы настройки интерактивных инструментов

Это отдельный поток после редакторского ядра статей; текущие JSON-форматы остаются форматом хранения.

1. Разложить `Tools` на вкладки «Содержание», «Поля», «Логика», «Результаты», «Интеграция», «SEO».
2. Заменить редактирование условий, ответов тестов и маппингов JSON-полями с визуальными селекторами; оставить стабильные технические ключи под контролем.
3. Для `DataTables.rows[].values` сделать табличный ввод по определённым колонкам, сохранив период действия и источник.
4. Скрывать низкоуровневые параметры от редакторов, которым достаточно менять подписи и тексты.
5. Не менять runtime и DSL без отдельного обоснования; форма должна редактировать текущую модель данных.

**Критерии приёмки:** редактор может изменить текст и типовые значения инструмента без ручного редактирования JSON; сложные правила остаются валидируемыми текущими функциями.

## Общие правила для агента

- Выполнять этапы по порядку и не смешивать миграцию содержимого с изменением визуального шаблона.
- На каждом этапе сначала показать затронутые модели и способ сохранения обратной совместимости, затем менять код.
- Для миграций контента сначала делать отчёт и dry run; при неизвестном формате останавливать только соответствующие записи и сохранять их для ручного разбора.
- Не менять URL существующих страниц без отдельного согласования.
- После этапов 1–4 вручную сверять контрольные статьи в админке и в preview; после каждого этапа фиксировать результат и список оставшихся записей.
- Этапы 7 и 8 не блокируют публикацию первых улучшений редактора статей.

## Итоговое состояние

Редактор создаёт абзацы, заголовки, списки и таблицы обычным интерфейсом; старые блоки представлены настоящими редактируемыми блоками; опубликованная страница и черновик доступны в полном визуальном preview; страницы видны в редакционной иерархии; внутренние ссылки выбираются из CMS; SEO- и миграционные данные отделены от основного потока написания.
