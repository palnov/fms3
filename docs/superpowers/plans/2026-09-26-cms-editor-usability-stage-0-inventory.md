# Предварительная инвентаризация CMS: этап 0

Дата: 30 сентября 2026 года
Статус: этап 0 завершён. Production-инвентаризация снята read-only запросами; резервная копия восстановлена в отдельную изолированную PostgreSQL 16 и сверена с baseline.

## Результат проверки окружения

- В рабочем окружении `DATABASE_URL` не задан. В `.env.local` есть только настройки интеграции Pravoved; адрес CMS-БД там отсутствует.
- Payload по умолчанию ожидает PostgreSQL на `localhost:5432`, но локального слушателя на этом порту нет.
- Команд `pg_dump` и `psql` в PATH нет. Docker CLI установлен, но Docker daemon недоступен; локальной PostgreSQL-службы не найдено.
- Локальный Payload Local API недоступен. Live-счётчики сняты напрямую с production PostgreSQL только read-only SQL-запросами. База данных и копия MDX — разные источники; MDX-файлы не использовались как замена backup.
- В этапе 0 backfill и любые записи в документы Pages не запускались. Для этапа 1 сначала восстановить отдельную тестовую БД из проверенного backup; production Pages не использовать для пробного backfill.
- При последующем локальном чтении через Payload выставить `PAYLOAD_DB_PUSH=false`: конфигурация включает schema push в непроизводственном окружении по умолчанию.

## Проверка удалённого контура

- В `dostup2.txt` есть данные для веб-доступа и сервера; секреты в отчёт не копировались. Файл исключён из Git через `.gitignore`.
- HTTPS-сайт отвечает; его DNS-адрес совпадает с IP сервера из файла. SSH-порт 22 доступен с рабочей машины, PostgreSQL-порт 5432 напрямую недоступен. Это совместимо с БД во внутренней сети или контейнере и не доказывает отсутствие удалённой БД.
- Публичная страница `/cms` отвечает кодом 200, но путь `/api/cms/pages`, заданный текущей локальной конфигурацией Payload, отвечает 404. Перед использованием API нужно сверить конфигурацию реально развёрнутой версии.
- SSH-аутентификация настроена пользовательским ключом PuTTY (`.ppk`) через Pageant. Сервер принял соответствующий публичный ключ; пароль и приватный ключ в отчёт не копировались.
- 30.09.2026 read-only SSH-инвентаризация подтвердила Ubuntu 24.04, Docker и PostgreSQL 16.15. Контейнер основного сайта подключён к базе `fms3`; отдельная база `payload` принадлежит другому приложению и не содержит таблицы `pages`.
- Попытка сохранить custom-format `pg_dump` базы `fms3` локально через защищённый файловый поток была отклонена автоматической политикой выполнения до старта процесса (`blocked by policy`). Дамп не создавался и данные БД не экспортировались. Не повторять экспорт обходным способом.
- Чтобы не передавать production-данные на рабочую машину, backup создан непосредственно на сервере: `/var/backups/fms3-stage0/fms3-prod-20260930.dump` (custom format, 844 094 байта, файл `0600`, родительский каталог `0700`). `pg_restore --list` завершился успешно; SHA-256: `a55490d03d79b06b8fabd17365b46b94b0cd930b5f068a4bf2f42fce96ee5979`.
- Полный restore проверен в отдельном контейнере PostgreSQL 16 с `--network none`, без опубликованных портов и без внешних подключений. Восстановленная БД `fms3_stage0_verify` имела размер 15 MB. После сверки временный контейнер и его временный том удалены; защищённый backup сохранён на сервере.
- `/dostup2.txt` подтверждённо исключён из Git (`git check-ignore`); его значения и секреты в отчёт не копировались.
- Для будущего чтения через Payload Local API указывать `PAYLOAD_DB_PUSH=false` и подключать только тестовую копию. Не направлять локальную Payload-конфигурацию на production: при `NODE_ENV` отличном от `production` schema push включён по умолчанию.

## Проверка конфигурации и решения

- В проекте установлены Next.js 16.2.9 и Payload 3.88.0. `Pages` использует Lexical и `BlocksFeature`; `EXPERIMENTAL_TableFeature` в редакторе не включён.
- Публичный рендерер уже умеет выводить Lexical-узлы таблиц, но сохранённый вывод всех ячеек сейчас преобразуется в `<td>`.
- Публичные маршруты читают Next Draft Mode; подключённой конфигурации Payload Live Preview в админке не найдено.
- Backfill `CMS_BLOCK_n` должен материализовать настоящие Lexical block nodes из `legacyMarkdown`; текущий runtime-восстановитель не является исправлением содержимого, показанного в Payload Admin.
- Предварительный вариант для следующего этапа — пилот установленного Table Feature с ручной проверкой совместимости. Если он нестабилен для редактора, использовать отдельный блок таблицы в статье.
- Кандидаты на иерархию существуют в статических маршрутах: например `/pathways/citizenship/oath` → `/pathways/citizenship` и `/pathways/rvp/after-receiving` → `/pathways/rvp`. Назначать CMS-parent связи автоматически можно только после сверки с фактическими Pages.

## Завершение этапа 0

- Backup сохранён на сервере вне Git, его архив читается `pg_restore`, а полное восстановление в изолированный тестовый PostgreSQL прошло успешно.
- После restore счётчики совпали с production baseline: 44 Pages (32 article, 2 landing, 7 legal, 3 policy), 44 опубликованные, 39 страниц с 313 маркерами, SEO-поля заполнены на всех 44, `pages_rels` пуст, 11 `pages_blocks_*` таблиц содержат 0 строк; версия `_pages_v` также совпала (89 старых опубликованных, 43 latest опубликованных, 1 latest draft autosave).
- Все шесть контрольных публичных маршрутов на момент проверки вернули HTTP 200. В HTML без скриптов не найдено видимых `CMS_BLOCK_n`; это подтверждает публичное отображение, но не заменяет последующую проверку редакторской формы.
- Этап 0 закрыт без изменений схемы и документов production Pages. Временная тестовая БД после сверки удалена; перед этапом 1 её можно заново восстановить из сохранённого backup. Перед тестовым чтением через Payload использовать `PAYLOAD_DB_PUSH=false`.
