# Payload CMS и no-code runtime для контента и инструментов

Дата: 2026-09-02

## 1. Цель

Встроить Payload CMS в существующее приложение FMS3 и сделать Payload источником правды для:

- всех информационных страниц и их содержимого;
- всех текстов внутри `/tools/*`;
- правил, формул, полей, ветвлений и результатов калькуляторов;
- сценариев Path Finder и шаблонов чек-листов;
- конфигурации проверок, AI-поведения и разрешённых API-операций.

Новая информационная страница, калькулятор или decision-tree-сценарий должны создаваться и публиковаться из Payload без изменения исходного кода. Существующие URL и тексты должны сохраниться.

Логика исполнения будет декларативной: Payload хранит данные и правила, а приложение исполняет их через типизированный безопасный runtime. Произвольный JavaScript из базы данных никогда не исполняется.

## 2. Текущий контекст и границы

Проект использует Next.js 16 App Router, React 19, TypeScript, Tailwind CSS 4, MDX, SQLite для `knowledge.db` и журнала AI, а также Redis для rate limiting. В текущем репозитории есть 39 MDX-страниц и 10 страниц инструментов.

В Payload переходят:

- 39 текущих MDX-страниц в `legal`, `pathways`, `mmc-saharovo` и `po-voprosam-migracii`;
- главная страница, каталог `/pathways`, `/privacy`, `/editorial-policy` и `/karta-sayta`;
- весь пользовательский текст на страницах `/tools/*`.

В коде остаются:

- React-компоненты и общий визуальный runtime;
- алгоритмы исполнения декларативных правил;
- серверные адаптеры внешних проверок;
- RAG, rate limiting, безопасность, cookies и работа с секретами;
- текущие API `/api/leads`, `/api/consultant`, `/api/health`;
- SQLite-базы знаний и журнала AI на первом этапе.

Новые внутренние калькуляторы, сценарии, чек-листы и ветвления не требуют изменения кода. Подключение нового внешнего API без кода возможно только через заранее реализованный безопасный HTTP-коннектор и разрешённый тип провайдера.

## 3. Рассмотренные подходы

### 3.1. Декларативный domain-specific runtime — выбранный подход

Payload хранит поля, вопросы, условия, формулы, таблицы данных и результаты. Общий runtime интерпретирует эти структуры и строит интерфейс.

Плюсы:

- новые калькуляторы и сценарии создаются без deploy;
- конфигурация валидируется до публикации;
- можно сделать версии, draft/publish, тестовые кейсы и откат;
- нет выполнения произвольного кода из CMS.

Минус — сначала требуется реализовать типизированный движок и удобный админский редактор.

### 3.2. Технические JSON Schema/JSON Logic-объекты

Схемы форм и условий хранятся в стандартизированном JSON. Это ускоряет создание runtime, но без кастомного интерфейса будет неудобно редакторам и повысит риск некорректных конфигураций.

Этот подход используется внутри выбранного варианта как формат хранения, но не показывается редактору в виде сырого JSON.

### 3.3. Полноценный визуальный workflow-builder

Редактор соединяет узлы вопросов, условий и результатов на графе. Это наиболее гибкий вариант, но он заметно дороже в реализации и сложнее для валидации.

На первом этапе используется устойчивый form/block-based редактор с предпросмотром. Графическое представление можно добавить поверх той же модели позже, не меняя runtime.

## 4. Архитектура

Payload встраивается в тот же Next.js-проект. Админка монтируется на `/cms`, Payload REST API — на `/api/cms`, чтобы не пересекаться с существующим `/admin/ai-chats` и прикладными API. Публичный frontend получает CMS-данные через Payload Local API на сервере, а не через собственный HTTP-запрос к тому же приложению.

Хранилища:

- Payload — PostgreSQL через `@payloadcms/db-postgres`;
- медиа — persistent directory на текущем `/data` volume на первом этапе;
- `knowledge.db` и `ai-chat-log.db` — остаются SQLite;
- Redis — остаётся общим rate-limit store.

Схема потока:

```text
Payload Admin / редактор
        ↓ draft + publish
PostgreSQL и Media
        ↓ Local API: только published или preview draft
Next server components
        ↓ typed config
No-code runtime
        ↓
Calculator / Scenario / Checklist / Checker / AI UI
```

## 5. Модель данных Payload

### 5.1. `Pages`

Коллекция для информационных страниц с полями:

- `path` — уникальный полный URL, всегда начинается с `/`;
- `kind` — `article`, `landing`, `legal`, `policy`;
- `title`, `description`, `tags`;
- `reviewedAt`, `readingTime`;
- `content` — Lexical Rich Text;
- `seo` — title, description, canonical, noindex, Open Graph image;
- связи `relatedPages`;
- draft/publish и versions.

Стандартные Markdown-элементы сохраняются как заголовки, абзацы, списки, таблицы, ссылки и изображения. Текущие MDX-компоненты переводятся в безопасные блоки:

- `QuickAnswer`;
- `Notice`;
- `Warning`;
- `LegalSource`;
- `FaqAccordion`;
- `RelatedGuide`;
- `LinkCardGrid`;
- `ConsultationBanner`.

`ArticleMeta` становится группой полей страницы, а не исполняемым компонентом в контенте.

### 5.2. `Tools`

Коллекция для всех инструментов с полями:

- `slug` — полный публичный путь, например `/tools/patent-cost`;
- `toolType` — `calculator`, `scenario`, `checklist`, `checker`, `ai`;
- `title`, `description`, `eyebrow`;
- `seo`;
- `definition` — типизированная декларативная конфигурация;
- `uiCopy` — labels, placeholders, подсказки, CTA, сообщения загрузки, ошибки и результаты;
- `providerKey` — только для заранее зарегистрированных внешних адаптеров;
- `testCases`;
- draft/publish и versions.

Стабильные ключи полей и операций используются runtime, а видимые подписи хранятся в CMS. Редактор не может случайно изменить внутренний идентификатор, необходимый для работы движка.

### 5.3. `DataTables`

Версионируемые таблицы данных для ставок, регионов, сроков, коэффициентов и иных значений:

- ключ таблицы;
- строки с типизированными колонками;
- период действия `validFrom`/`validTo`;
- источник и дата проверки;
- статус публикации.

### 5.4. `RuleTestCases`

Тестовые входные данные и ожидаемые результаты для калькуляторов и сценариев. Публикация конфигурации запрещена, если обязательные тесты не проходят.

### 5.5. `Media`, `Users`, `SiteSettings`, `Redirects`

- `Media` — изображения и файлы с контролируемым доступом;
- `Users` — Payload auth users с ролями `admin`, `editor`, `publisher`;
- `SiteSettings` — меню, футер, главная страница, общие CTA и настройки сайта;
- `Redirects` — управляемые 301/308 redirects с проверкой циклов.

## 6. No-code runtime

### 6.1. Поля и формы

Поддерживаются типы:

- text, textarea;
- number, currency;
- date, date range;
- select, radio, checkbox, multi-select;
- repeatable group;
- relation to Page/DataTable;
- calculated read-only field.

У каждого поля есть стабильный key, label, help text, required, default value, validation и правила видимости.

### 6.2. Условия

Условия хранятся в ограниченном AST/JSON DSL. Поддерживаются `equals`, `notEquals`, `in`, `notIn`, `contains`, `exists`, сравнения чисел и дат, `and`, `or`, `not`.

Операторы работают только с известными типами и полями. Произвольные имена функций, JS-код, SQL и сетевые вызовы из условия запрещены.

### 6.3. Формулы

Разрешённые операции:

- арифметика и округление;
- проценты;
- min/max;
- разница и добавление календарных дней/месяцев;
- lookup по `DataTables`;
- нормализация строк и чисел;
- условное значение.

Формулы компилируются в безопасное внутреннее представление до публикации. Runtime не использует `eval`, `new Function` или выполнение пользовательского кода.

### 6.4. Сценарии

Сценарий состоит из упорядоченных шагов:

- question;
- information;
- branch;
- calculation;
- checklist;
- result;
- related page/CTA.

Переходы имеют условия. Валидатор проверяет наличие стартового шага, достижимость результатов, отсутствие циклов и ссылки только на опубликованные сущности.

### 6.5. Результаты

Результат содержит status, title, body template, calculated values, ссылки на Pages, CTA и условия отображения. Подстановка переменных выполняется безопасным шаблонизатором с whitelist переменных.

## 7. Интеграция инструментов

### 7.1. Калькуляторы

Текущие расчёты 90/180 и стоимости патента переводятся в DataTables и декларативные формулы. Новый калькулятор создаётся из полей, таблиц, формулы и результатов в `/cms`.

### 7.2. Path Finder и чек-листы

Вопросы, варианты, ветвления, документы, обязательность и ссылки переносятся в Payload. Общий renderer показывает шаги и сохраняет пользовательский прогресс на клиенте.

### 7.3. Проверки документов

Поля, подписи, маски, тексты состояний и mapping ответа редактируются в Payload. Реальные сетевые запросы выполняются зарегистрированным provider adapter. Секреты, base credentials, timeout limits и allowlist доменов не попадают в CMS.

### 7.4. AI

В Payload редактируются версии системных инструкций, тон, структура ответа, сообщения, source filters и безопасные границы retrieval settings. OpenRouter key, RAG implementation, sanitization, rate limit и обязательные security policies остаются в коде.

### 7.5. API

Payload управляет разрешёнными операциями, feature flags, полями запросов, timeout в заданном диапазоне, response mapping и пользовательскими сообщениями. Прикладные route handlers и allowlist провайдеров остаются в коде.

## 8. Публикация, безопасность и кэширование

Для Pages, Tools, DataTables и глобальных настроек включаются versions и drafts. Редакторы сохраняют черновики, publisher/admin публикует. Draft-доступ разрешён только авторизованным пользователям.

Перед публикацией hooks выполняют:

1. проверку схемы и типов;
2. проверку уникальности path/key;
3. проверку формул и ссылок;
4. проверку циклов и достижимости шагов;
5. запуск обязательных RuleTestCases;
6. проверку допустимых providerKey и параметров.

Runtime читает только опубликованную конфигурацию, кэширует её по версии и очищает соответствующие Next cache tags после публикации. Preview использует draft mode и отдельный server-side read path.

Ошибки конфигурации блокируют publish. Ошибка CMS в production отдаёт sanitized 503 для динамического CMS-route и не раскрывает credentials или внутреннюю структуру. Во время миграции допускается временный feature flag с fallback на MDX; после подтверждения паритета fallback отключается.

## 9. Маршрутизация и SEO

Информационные URL обслуживаются CMS-driven route по точному `Pages.path`. После проверки текущие MDX route files убираются из Next route tree, а исходники сохраняются как migration fixtures до завершения cutover.

Страницы `/tools/*` получают контент и metadata из `Tools`, а интерактивный runtime получает сериализованную конфигурацию через server/client boundary. Новый опубликованный `Tool` автоматически доступен по `/tools/<slug>`.

`generateMetadata`, canonical, Article/Breadcrumb JSON-LD и sitemap строятся из опубликованных Pages/Tools. Текущие URL, redirects и `robots.txt` сохраняются.

## 10. Миграция существующего контента

Создаётся идемпотентный migration script:

1. читает 39 MDX-файлов и текущую карту `src/lib/articles.ts`;
2. разбирает MDX AST, а не регулярными выражениями;
3. преобразует Markdown-ноды в Lexical;
4. преобразует текущие компоненты в Payload blocks;
5. переносит metadata из page/layout файлов;
6. импортирует tool copy, input definitions и текущие rules в стартовые Tool documents;
7. создаёт DataTables и тестовые кейсы;
8. повторный запуск обновляет документы по стабильному source key, не создавая дубликаты.

До удаления старых маршрутов проверяются количество документов, уникальность путей, извлечённый текст, ссылки, заголовки, таблицы, FAQ, metadata и видимый результат каждого инструмента.

## 11. Ошибки и отказоустойчивость

- неизвестный path — `notFound()`;
- невалидный published document — sanitized application error и alert в логах без содержимого секретов;
- недоступен Postgres — sanitized 503 для CMS-dependent route;
- недоступен внешний provider — существующий контролируемый error state инструмента;
- отсутствует DataTable row — publish validation error или понятный runtime result;
- устаревшая версия правила — выбор записи по effective dates, без молчаливого fallback на случайное значение;
- битая ссылка или циклический redirect — блокировка публикации.

## 12. Тестирование

Unit-тесты:

- evaluator условий;
- формульный engine и типы;
- операции дат и округления;
- lookup/effective dates;
- шаблоны результатов;
- валидатор графа сценария;
- response mapping и ограничение provider config.

Integration-тесты:

- Payload collections и access control;
- draft/publish/rollback;
- блокировка публикации невалидных конфигураций;
- миграция MDX и повторный запуск;
- Local API published vs draft;
- cache invalidation.

E2E-тесты:

- все 39 информационных URL;
- главная, каталог и policy pages;
- все текущие `/tools/*`;
- один новый калькулятор, созданный только через seed/admin config;
- один новый branching-сценарий, созданный только через seed/admin config;
- preview, 404, redirects, sitemap и CMS login.

Финальная проверка выполняет существующий `npm run check` и отдельный route/content parity report.

## 13. Этапы внедрения

1. Подключить Payload, Postgres adapter, config, route group `/cms` и миграции.
2. Создать collections, роли, access control, media storage и generated types.
3. Реализовать Lexical renderer и MDX migration script.
4. Перенести все Pages и сохранить текущий визуальный рендеринг.
5. Реализовать DSL, validator, formula engine и generic Tool runtime.
6. Перевести калькуляторы, Path Finder и чек-листы на конфигурацию.
7. Перевести tool copy, checker mappings, AI config и API settings.
8. Добавить custom Payload editor, test runner, preview и publish validation.
9. Провести parity/E2E проверки, отключить MDX fallback и удалить старые route files.
10. Обновить Docker/Coolify env и production migration workflow.

## 14. Критерии готовности

Система считается внедрённой, когда:

- все существующие информационные страницы открываются по прежним URL;
- их контент и metadata доступны для редактирования в Payload;
- все тексты `/tools/*` редактируются в Payload;
- новый калькулятор создаётся и публикуется без изменения TypeScript;
- новый branching-сценарий создаётся и публикуется без изменения TypeScript;
- новый чек-лист создаётся без изменения TypeScript;
- invalid config невозможно опубликовать;
- опубликованная конфигурация версионируется и откатывается;
- runtime не исполняет код из CMS;
- текущие AI, API, Redis, Feedot и SQLite-функции не регрессируют;
- `npm run check` и route/content parity report проходят.

## 15. Осознанные ограничения

No-code распространяется на все возможности, выражаемые поддержанными полями, условиями, формулами, таблицами и provider mappings. Произвольный новый UI-виджет или полностью новый внешний протокол потребует расширения runtime или кода адаптера. Это ограничение сохраняет безопасность и предсказуемость production-системы.
